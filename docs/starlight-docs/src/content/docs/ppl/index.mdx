Piped Processing Language (PPL) is the **native query language** of the OpenSearch Observability Stack. Every log query, every trace investigation, and every pattern analysis flows through PPL - a pipe-delimited language designed for the way operators and engineers actually think about data.

<PlaygroundLink query="" text="Try PPL now in the live playground →" />

```sql
source = logs-otel-v1*
| where severityNumber >= 17
| stats count() as errors by `resource.attributes.service.name`
| sort - errors
```

<PlaygroundLink query="%7C%20where%20severityNumber%20%3E%3D%2017%20%7C%20stats%20count%28%29%20as%20errors%20by%20%60resource.attributes.service.name%60%20%7C%20sort%20-%20errors" />

That query finds every error log, counts them by service, and sorts by severity - all in four lines you can read aloud. No JSON nesting, no callback syntax, no query DSL to memorize.

## Why PPL?

### Think in pipelines, not in trees

PPL follows the natural mental model of data investigation: start with a data source, progressively filter, transform, and aggregate. Each pipe (`|`) represents a single, composable operation. Reading a PPL query from top to bottom tells you exactly what happens at every step.

```sql
source = otel-v1-apm-span-*
| where serviceName = 'frontend'
| where durationInNanos > 2000000000
| stats avg(durationInNanos) as avg_latency by name
| sort - avg_latency
| head 10
```

### One language across logs and traces

Unlike platforms that require different query dialects for different signal types, PPL works across **both logs and traces** in the Observability Stack. The same syntax, the same commands, the same muscle memory - whether you are triaging an incident in logs or profiling latency in traces.

| Signal  | Query Language | Index Pattern           |
|---------|---------------|-------------------------|
| Logs    | **PPL**       | `logs-otel-v1*`         |
| Traces  | **PPL**       | `otel-v1-apm-span-*`   |
| Metrics | PromQL        | Prometheus time-series  |

### Designed for observability at scale

PPL is not a general-purpose query language bolted onto a search engine. It was designed from the ground up for the workflows observability engineers perform daily:

- **Pattern discovery** - the `patterns` command automatically extracts log patterns and clusters similar entries, replacing hours of manual regex work
- **Field extraction on the fly** - `parse`, `grok`, and `rex` let you extract structured fields from unstructured log text without re-indexing
- **Statistical analysis** - `stats`, `eventstats`, `streamstats`, and `trendline` cover everything from simple counts to rolling window calculations
- **Deduplication and ranking** - `dedup`, `top`, and `rare` surface the signal in noisy data
- **Machine learning built in** - `ml` and `kmeans` run anomaly detection and clustering directly in your query pipeline
- **Join and correlate** - `join`, `lookup`, `append`, and `subquery` combine data from multiple indices for cross-signal investigation

## PPL in the Observability Stack

PPL is woven into every investigation surface of the stack:

### Discover

The **Discover** interface for [Logs](/docs/investigate/discover-logs/) and [Traces](/docs/investigate/discover-traces/) uses PPL as its primary query language. Type PPL directly in the query bar, with autocomplete for field names, commands, and functions.

### Claude Code plugin

The [Claude Code observability plugin](/docs/claude-code/) generates PPL queries from natural language. Ask "show me the slowest traces from the frontend service" and the plugin produces the PPL query, runs it, and returns results - all powered by PPL templates.

### Alerting and anomaly detection

PPL queries can drive [alerts](/docs/alerting/) and [anomaly detection](/docs/anomaly-detection/) monitors. Define alert conditions using the same query language you use for ad-hoc investigation.

### Dashboards

PPL query results can be [saved to dashboards](/docs/dashboards/) as live visualizations - line charts, bar charts, heatmaps, and more - all driven by PPL.

## Using the PPL API

Discover runs PPL queries through the `POST /_plugins/_ppl` endpoint, and you can call the endpoint directly. The following options help with queries over large, time-based indexes.

### Time-range index pruning

When a query covers an index pattern or data stream that spans many indexes, OpenSearch first skips the indexes that can't contain data in the query's time range, and only then resolves the schema. Fewer indexes means fewer shards to search, fewer point-in-time contexts to open, and fewer mapping conflicts between old and new indexes. Pruning applies to regular indexes and to the backing indexes of data streams.

OpenSearch takes the time range from either of two places:

- A range on `@timestamp`, `timestamp`, or `time` in the query itself.
- The `time_field`, `start_time`, and `end_time` request parameters. Discover sends these with the time range you pick. See [Time range and index pruning](/docs/investigate/discover-logs/#time-range-and-index-pruning).

| Parameter | Description |
|-----------|-------------|
| `start_time`, `end_time` | The inclusive bounds of the time window. Both are required. Accepts date math (`now-7d`), ISO-8601 (`2026-02-01T00:00:00Z`, `2026-02-01`), epoch milliseconds, or `2026-02-01 00:00:00`. A value that can't be used is ignored, and nothing is pruned. |
| `time_field` | The field the bounds apply to. Defaults to `@timestamp`. |

```bash
curl -X POST "localhost:9200/_plugins/_ppl" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "source=logs-otel-v1* | where `time` >= \"2026-02-01 00:00:00\" and `time` <= \"2026-02-01 01:00:00\" | stats count() by severityText",
    "time_field": "time",
    "start_time": "2026-02-01 00:00:00",
    "end_time": "2026-02-01 01:00:00"
  }'
```

<Aside type="caution">
The request parameters select indexes. They don't filter rows. Send only a window that the query's own `where` clause already restricts. If the query's range is wider than the bounds, rows in the skipped indexes are missing from the results.
</Aside>

Only the outermost `source=` is pruned. The other side of a `join`, a subsearch, a `multisearch` dataset, and a `lookup` table are read in full.

Pruning is experimental and is controlled by the `plugins.query.pruning.enabled` cluster setting, which is on by default. It needs the `indices:admin/resolve/index` and `indices:data/read/field_caps*` permissions, which the `ppl_full_access` role grants. Without them, the query reads every index that matches.

### Asynchronous queries

A long-running query can return before it finishes. Add `wait_for_completion_timeout` to the request body:

| Parameter | Default | Description |
|-----------|---------|-------------|
| `wait_for_completion_timeout` | `30s` | How long the request waits for the query to finish, from `0s` to `60s`. If the query finishes in time, the response is a regular PPL response. Otherwise, the response contains the query's `id`. |
| `keep_alive` | `5m` | How long OpenSearch keeps the result after the query finishes, up to `24h`. |

```bash
curl -X POST "localhost:9200/_plugins/_ppl" \
  -H "Content-Type: application/json" \
  -d '{"query": "source=logs-otel-v1* | stats count() by `resource.attributes.service.name`", "wait_for_completion_timeout": "5s", "keep_alive": "10m"}'
```

If the query is still running when the wait expires, the response looks like this:

```json
{
  "id": "<opaque-id>",
  "status": "RUNNING",
  "progress": {"fraction_done": 0.42},
  "schema": [],
  "datarows": [],
  "total": 0
}
```

`progress.fraction_done` is an estimate, from `0.0` to `1.0`, of how much of the query's index scans has completed. It never decreases between polls and is `1.0` once the query succeeds.

Use the `id` to follow up on the query:

| Request | Description |
|---------|-------------|
| `GET /_plugins/_async_query/<id>` | Returns the query's status. Poll until the status is `SUCCEEDED`, which returns the `schema` and `datarows`, or `FAILED`, which returns an `error` object. Returns `404` after `keep_alive` expires. |
| `DELETE /_plugins/_async_query/<id>` | Cancels a running query, which returns the status `CANCELLED`, or discards a finished query's result. |

The `_explain` endpoint, requests with `"profile": true`, and non-JSON response formats (`csv`, `raw`, `viz`) always run synchronously. Submitting a query requires the `cluster:admin/opensearch/ppl` permission, fetching a result requires `cluster:admin/opensearch/ql/async_query/result`, and deleting one requires `cluster:admin/opensearch/ql/async_query/delete`. With the Security plugin enabled, only the user who submitted a query can fetch or delete it.

## How PPL compares

PPL belongs to the family of pipe-based query languages used in modern observability platforms. If you have experience with Kusto Query Language (KQL) or Elastic Event Query Language (EQL), PPL will feel immediately familiar - with key advantages:

| Capability | PPL | KQL (Kusto) | EQL (Elastic) |
|-----------|-----|-------------|----------------|
| Pipe-based syntax | Yes | Yes | Limited |
| Log pattern discovery | Built-in (`patterns`) | Requires external tooling | No |
| Machine learning in-query | `ml`, `kmeans` | Separate service | Separate service |
| Field extraction on-the-fly | `parse`, `grok`, `rex` | `parse`, `extract` | Limited |
| Join across indices | `join`, `lookup`, `subquery` | `join`, `lookup` | Sequence only |
| Rolling statistics | `streamstats`, `trendline` | `scan`, window functions | No |
| Open source | Fully open source (Apache 2.0) | Proprietary | Proprietary (SSPL) |
| OpenTelemetry-native | First-class OTel support | Via connector | Via integration |
