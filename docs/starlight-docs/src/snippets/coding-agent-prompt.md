# Instrument this agent for OpenSearch Agent Traces and Agent Evaluations

Instrument the agent app in this repository so every run shows up in OpenSearch **Agent Traces** and its quality scores in **Agent Evaluations**. Use the OpenSearch GenAI Observability SDK and the OpenTelemetry GenAI semantic conventions. Read the SDK's README and `docs/agent-evaluations.md` first, and use only APIs that exist in the installed version.

Values: OTLP endpoint `<OTLP_ENDPOINT>` (base URL, for example `http://localhost:4318`), service `<SERVICE_NAME>`, agent `<AGENT_NAME>`, version `<AGENT_VERSION>`, test suite `<SUITE_NAME>`.

## 1. Install and register
- Python: `pip install opensearch-genai-observability-sdk-py`. TypeScript: `npm install @opensearch-project/genai-observability-sdk-ts @opentelemetry/context-async-hooks`. If npm fails with `ERESOLVE` against the framework's OpenTelemetry 2.x peers, install with `--legacy-peer-deps`, keep that in `.npmrc`, keep `@opentelemetry/api` on 1.9.x, run the unchanged app once and add back any peer it now misses (Strands: `@modelcontextprotocol/client`).
- Call `register()` once at startup, before the agent is built: Python `register(service_name=, agent_name=, agent_version=)`; TypeScript `await register({ serviceName, agentName, agentVersion })`, preceded by `context.setGlobalContextManager(new AsyncLocalStorageContextManager().enable())` so async spans nest.
- Endpoint from the environment, never hardcoded: `OTEL_EXPORTER_OTLP_ENDPOINT=<OTLP_ENDPOINT>` (the SDK appends `/v1/traces` and `/v1/logs`). Separate pipelines: set both traces and logs URLs (`traces_endpoint` + `logs_endpoint`, or both `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` and `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`; Data Prepper defaults 21890 and 21892). Amazon OpenSearch Ingestion (OSIS): HTTPS only, `sigv4={"service": "osis", "region": ...}` behind a config switch, `compression` equal to the pipeline's. Evaluation results travel as OTLP **logs**, so the logs path must work too.
- Do not call the framework's own exporter setup (`StrandsTelemetry().setup_otlp_exporter()`, Strands `setupTracer()`): `register()` owns the global tracer provider. Flush before a script exits: `provider.force_flush()` / `await provider.forceFlush()`.

## 2. Traces, spans and sessions
- One trace per agent turn (one user request). Its **root span is the agent span**: `gen_ai.operation.name=invoke_agent`, `gen_ai.agent.name`, `gen_ai.agent.version`, `gen_ai.conversation.id` (stable for the whole conversation; it builds Sessions), `gen_ai.input.messages` / `gen_ai.output.messages` as JSON in the GenAI parts format `[{"role": "user", "parts": [{"type": "text", "content": "..."}]}]`, and the token usage of **this turn only**.
- Wrap each turn: Python `@observe(name="<AGENT_NAME>", op=Op.INVOKE_AGENT)` on a function or method that takes the user input, TypeScript `withObserve("<AGENT_NAME>", { op: Op.INVOKE_AGENT }, async (span) => ...)`. Inside it call `mark_agent_root()` / `markAgentRoot()` and `enrich(session_id=<conversation id>, input_messages=..., output_messages=..., **{"gen_ai.agent.version": "<AGENT_VERSION>"})` (TypeScript `enrich({ sessionId, inputMessages, outputMessages, "gen_ai.agent.version": ... })`); `enrich` messages replace the automatic argument capture. Return the agent span's hex `trace_id` / `span_id` with the answer, for evaluations.
- Let framework auto-instrumentation produce the inner spans: Strands, LangChain, OpenAI and others emit `invoke_agent`, `chat` (with `gen_ai.usage.input_tokens` / `output_tokens`, `gen_ai.request.model`) and `execute_tool` spans through the global provider. Give the framework agent the same name `<AGENT_NAME>` and pass it the conversation id (Strands `trace_attributes` / `traceAttributes` with `gen_ai.conversation.id`). For Strands set `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental,gen_ai_span_attributes_only` (messages as span attributes) and, in Python, also `gen_ai_use_latest_invocation_tokens`; Strands TypeScript reports lifetime token totals, so set this turn's usage on your agent span (`enrich({ inputTokens, outputTokens })` from `result.metrics.agentInvocations.at(-1).usage`). Wrap with `observe(op=Op.EXECUTE_TOOL)` / `observe(op=Op.CHAT)` + `enrich(model=, input_tokens=, output_tokens=)` only what is not traced.
- Root rules: if the agent runs inside an HTTP handler or job span, mark the agent span with `mark_agent_root()` (span attribute `derived.gen_ai.is_root=true`). Never continue an incoming `traceparent` whose parent span is not exported to the same OpenSearch: start a new root instead, or the trace has no root.
- Never put secrets or credentials in attributes.

## 3. Evaluations (each score is one `gen_ai.evaluation.result` log event)
- **Online** (live traffic: after each turn or in a sampled job): `score(name, value, trace_id=, span_id=` of the agent span`, conversation_id=, evaluator=, evaluator_type="code" | "llm_judge" | "human", evaluator_description=, threshold=` (or `label="pass"/"fail"`)`, score_min=, score_max=)`; TypeScript `score({ name, value, traceId, spanId, conversationId, evaluator, evaluatorType, ... })`, always with `traceId` / `spanId`.
- **LLM judges**: add `judge_model`, `judge_prompt_name`, `judge_prompt_version` (camelCase in TypeScript); never put the judge's system prompt on results (no `judge_system_instructions`). Don't trace the judge as your agent (no `invoke_agent`, not `<AGENT_NAME>`); if you trace it, pass its trace id as `judge_trace_id`.
- **Offline** suite: a dataset file of cases with a stable case id, case name, input and expected output. Synchronous Python: `evaluate(name="<SUITE_NAME>", task=, data=[{"case_id", "case_name", "input", "expected"}], scores=[...], run_name=, run_description=, agent_name=, agent_version=)` with scorers declared by `@scorer(name=, evaluator_type=, description=, threshold=, score_min=, score_max=, judge_model=, judge_prompt_name=, judge_prompt_version=)`. Async agents (all TypeScript, Python asyncio): `Benchmark`; Python `Benchmark(name=, run_name=, agent_name=, agent_version=)` and `log(case_id=, case_name=, input=, output=, expected=, trace_id=, span_id=, scores=[EvalScore(...)])`; TypeScript `new Benchmark("<SUITE_NAME>", { runName, agentName, agentVersion })` and `bench.log({ caseId, caseName, input, output, expected, traceId, spanId, scores })`; await each case yourself, then `close()`. Results get `test.suite.name`, `test.suite.run.id`, `test.case.id` / `test.case.name`, `opensearch.test.case.expected`.
- **CI**: expose the suite as one command that exits non-zero when an evaluation's mean is below its bar or a case errors. For GitHub Actions, adapt the Python SDK's `examples/github-action` (`action.yml`, `example-workflow.yml`; its `run_suite.py` calls `register()` itself, so the suite module must not register on import); in TypeScript write the equivalent workflow step. The SDK adds `cicd.pipeline.*` in CI itself.

## 4. Verify, then report
Run a two-turn conversation (score each turn online) and one offline suite run; flush; poll for up to 60 s (evaluation events can arrive later than spans); query OpenSearch (`_plugins/_ppl` or `_search`):
- `otel-v1-apm-span-*`: each trace has one root (`parentSpanId = ""`): your `invoke_agent` span with `attributes.gen_ai.agent.name`, `.agent.version`, `.conversation.id`, `.input.messages`, `.output.messages`, `.usage.*` and `derived.gen_ai.is_root`; below it `chat` spans with `gen_ai.usage.*` and `execute_tool` spans in the same trace; both turns share one conversation id, and turn 2's root tokens are not turn 1 + turn 2.
- `otel-v1-genai-evaluation*`: `eventName = gen_ai.evaluation.result` documents for the online scores (no `test.suite.run.id`) and the offline run (`test.suite.name`, `test.suite.run.id`, `test.case.id`), whose `traceId` / `spanId` match agent root spans, and no `gen_ai.system_instructions`. If they land in `logs-otel-v1-*`, the pipeline lacks the `eventName` route.
- If OpenSearch Dashboards is reachable: Agent Traces (Traces, Spans, Sessions tabs) and Agent Traces > Evaluations (its setup detects `otel-v1-genai-evaluation*`).

Checklist (confirm each with evidence):

- [ ] Online `score()` results attached to the agent span, with evaluator name, type, description and rule.
- [ ] Offline run with suite name, run id, stable case ids/names and expected output; judge model and prompt name/version, no judge system prompt.
